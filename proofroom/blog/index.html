When AI Agents Work Together, Who Checks the Gaps? Building ProofRoom with Switch

A hackathon build about shared context, cross-repository checks, and keeping humans in control.

An AI coding agent changes an API. Its tests pass. The change looks ready to ship.

Then a teammate’s application tries to read a field that no longer exists.

The agent completed its task, and the backend test suite is green. But a client depending on the API can no longer use the response. The failure lives between the pieces of software.

That’s the problem we explored with ProofRoom: a workflow designed to help people and coding agents share requirements, check compatibility, and review evidence together before approving a change.

We built it for the Flip the Switch Hackathon, hosted by WeMakeDevs and DevTools Academy and centred on Switch. The challenge was to bring an AI agent into a team conversation and use it to get real work done alongside people.

Our question was: what happens when the work involves more than one agent, more than one set of assumptions, and a human who needs to know what actually passed?

First, what is Switch?

Switch is open-source infrastructure for connecting AI agents with team chat.

You bring the agent and the chat tools you want to use. Switch connects them through a room: a shared space where people and agents can exchange messages, instructions, tasks, and context.

It does not replace your AI model or your chat application. Instead, it gives them a way to participate in a shared workflow.

For a first-time user, we found it helpful to think of a Switch room as:

A shared workspace where people and agents can coordinate around a task, rather than a private conversation with one assistant.

The Switch quickstart is a good starting point if you want to explore it yourself.

The problem: a green test suite isn’t the whole story

Our example centres on a checkout API. Suppose it initially returns:

JSON
{
  "total": 26.34
}

A backend agent receives a request to expose more pricing information. It updates the response to use grandTotal and adds a tax breakdown. The backend tests are updated and pass.

But an older client still expects:

JS
response.total

If total disappears, the client receives undefined. The backend may be working according to its new tests, but an existing consumer has lost a field it depends on.

That’s the gap we wanted ProofRoom to make visible:

A change can be correct in isolation and still break an agreement between systems.

What ProofRoom does

ProofRoom brings a backend agent, a verifier agent, and a human into a shared workflow.

  • The backend agent proposes and implements a change.
  • The verifier agent checks the effects, including compatibility with clients.
  • The human supplies requirements, reviews the evidence, and decides whether to approve.

In the documented room transcript, the backend changes the checkout response from total to grandTotal. The verifier reports that older clients relying on total would break.

The documented repair restores total as a deprecated alias while retaining grandTotal. This allows the new response to coexist with the older contract.

The point is not just to have a second agent say “looks good.” The workflow asks for a more useful handoff: what changed, what was checked, what failed, and which revisions were tested?

The room does not replace tests. It gives the people and agents a shared place to coordinate around the requirements, evidence, and decisions.

Why Switch matters to the workflow

Without shared context, each participant can have a different picture of the task.

The backend agent may know about the new API response. The verifier may know what the client expects. A human may know that an older mobile version is already in users’ hands and cannot be updated immediately.

A Switch room gives those participants a common place to communicate that information.

For ProofRoom, that means the requirement “older clients must keep working” can be discussed alongside the proposed change and its verification results. The human does not have to reconstruct the story from separate conversations.

The ProofRoom repository documents the workflow and includes its room instructions, demo application, client checks, and transcript.

Making the workflow visible

Agent coordination can be difficult to explain from text alone. A transcript is useful evidence, but it does not immediately show how the repositories, requirements, checks, and approval decision relate to one another.

So we also developed an interactive frontend on the feat/proofroom-frontend branch.

The experience tells the story in five chapters:

  1. Propose: a backend change passes its local checks.
  2. Discover: a client dependency breaks.
  3. Capture: a human adds a compatibility requirement.
  4. Verify: the workflow presents a repair and checks.
  5. Review: a human sees the revisions awaiting approval.

On desktop, a pinned, scroll-linked scene moves through the connected workspace. On smaller screens and for reduced-motion users, the experience offers manual chapter navigation.

The design goal was to turn an abstract coordination problem into something a reader could follow visually.

What is real, and what is simulated?

We think this distinction matters enough to state plainly:

Two parts of ProofRoom, with different scopes
ComponentScope
Switch-room workflowThe repository describes a workflow run through Switch and provides a room transcript, instructions, code, and reported test results.
Interactive frontendA simulated presentation of the ProofRoom concept. It does not itself connect to live Switch rooms, GitHub, or test runners.

The frontend is there to explain the workflow, not to impersonate a live integration. Its simulated activity is labelled accordingly.

Try the frontend

The frontend README lists Node.js 20.19+ or 22.12+ as a prerequisite.

BASH
git clone https://github.com/shahaman098/proofroom.git
cd proofroom
git checkout feat/proofroom-frontend
cd proofroom
npm ci
npm run dev

Open the local URL printed by Vite.

You can also run the frontend’s tests and production build:

BASH
npm test
npm run build

These commands test and build the frontend. They do not start the documented Switch-room workflow.

To explore that workflow, start with the main repository’s setup instructions and the Switch quickstart.

What we learned

1. Passing tests answer a specific question

A green backend suite tells us that the checks in that suite passed. It does not automatically prove that an older client or another service remains compatible.

The useful follow-up is: what assumptions sit outside this test suite?

2. Human context needs a path into verification

“Older clients must keep working” may begin as a message from a teammate. It becomes more actionable when it is shared with the agents and represented by a compatibility check.

A room makes the requirement visible; the check gives the team a way to evaluate it.

3. Evidence is more useful when it identifies the revisions

A statement such as “tests passed” is incomplete without knowing what was tested. If the code changes after verification, a previous approval may no longer apply.

ProofRoom’s approval concept is therefore tied to the specific revisions and requirements under review.

4. Human approval should stay deliberate

Agents can gather evidence and highlight problems, but the human should be able to understand the decision in front of them.

In the frontend, scrolling through the story does not approve a change. Presentation and approval are separate.

5. A prototype is stronger when its limits are clear

The frontend lets someone understand and explore the concept quickly. The documented Switch workflow shows a different, more technical part of the project.

Being clear about that boundary helps readers see both what exists now and what would be needed to connect the two.

What we would explore next

A next step would be to investigate whether the frontend could display real Switch-room events and verification evidence instead of simulated activity.

That would mean thinking carefully about permissions, where evidence comes from, and how to ensure that an approval refers to the exact revisions a person reviewed.

For now, ProofRoom has given us a way to explore a question that becomes increasingly important as teams use more coding agents:

It’s not enough for each agent to finish its own task. How do we help the whole team understand whether the pieces work together?
